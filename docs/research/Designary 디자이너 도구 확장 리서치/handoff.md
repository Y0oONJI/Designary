# 디자인–개발 핸드오프: 상태 명세, 명명, 단위·토큰 전달

## 1. 실제로 남아 있는 협업 문제는 무엇인가?

### Takeaway
화면의 치수보다 **상태가 발생하는 조건, 예외 처리, 공통 용어를 합의하는 일**에 작은 도구의 기회가 있다. 다만 이는 현업 사례와 과거 연구로부터의 방향성 추론이며, 2026년 한국 디자이너의 빈도·지불의사까지 검증된 수요는 아니다.

### Cited Findings
- **국내 현업 당사자 사례, 2021-10-20:** 우아한형제들 플랫폼디자이너 태주희는 기획·디자인·개발이 함께 Common/Edge/Corner 케이스, 데이터 IO/API 응답, 반응형 UI 피드백, 폼 유효성 인터랙션, 점검·장애 UI를 논의하여 규칙을 만들었다고 설명한다. React 컴포넌트라는 공통 언어가 불필요한 커뮤니케이션을 줄였다고 회고한다. 이는 실제 협업 문제의 사례이지 현재 국내 시장 전체를 대표하는 통계가 아니다. — [셀프서비스 디자인시스템 #1 – 디자이너 편](https://techblog.woowahan.com/6305/)
- **학술 현장조사, CHI 2023:** 미국 소프트웨어 조직 UX 실무자 114명 설문. 핸드오프 때 UI 동작을 설명하는 주석에 의존했고, 협업 도구 안의 과도한 정보도 혼란을 만들었다. 주석의 분량·구조에 가이드가 없을 때 작성 부담이 크다고 논의한다. 표본은 미국이며 Dev Mode 보편화 이전이다. 이를 현재 Figma에 주석이나 개발자 화면이 없다는 증거로 사용하면 안 된다. — [Feng, Li, Zhang, Understanding Collaborative Practices and Tools of Professional UX Practitioners in Software Organizations](https://arxiv.org/html/2302.11845v2)
- **제품사 실무 가이드, 2025-04-01:** Figma의 Jake Albaugh·Chad Bergman은 개발자에게 누락된 상태를 찾아 달라고 요청하고, 반응형 동작·고정값 여부·에셋 출처·기존 디자인 시스템에서 벗어난 이유를 설명하도록 권한다. 문제의 존재를 보여주는 실무 지침이며 발생률이나 해결 효과를 측정한 연구는 아니다. — [The designer’s handbook for developer handoff](https://www.figma.com/blog/the-designers-handbook-for-developer-handoff/)

### Inferences
- '이 버튼은 40px'보다 '어떤 조건에서 비활성화되는지, 제출 중 재클릭이 가능한지, 실패 후 입력이 남는지'를 기록하게 하는 도구가 위 근거에 더 잘 맞는다.
- 긴 체크리스트를 전부 보이게 하면 과잉 문서화 문제가 재현된다. 화면 유형에 필요한 질문만 보여주고, `미정`과 `해당 없음`을 구분하는 것이 낫다는 설계 가설이다.
- UI 용어집을 이미 사용하는 초급·소규모 팀 디자이너에게는, 용어를 검색한 다음 곧바로 상태 명세 초안을 복사하는 흐름이 자연스러울 수 있다. 성숙한 디자인 시스템 팀에는 기존 규칙과 겹칠 가능성이 크다.

### Gaps
- 한국 Figma 사용자의 2026년 상태 누락 빈도, 질문 왕복 시간, 수동 단위 변환 빈도에 대한 대표성 있는 최신 수치는 확보하지 못했다.
- 상태 표를 별도 브라우저에서 작성하는 비용이 Figma 주석을 직접 쓰는 것보다 작은지 검증이 필요하다.

## 2. Figma와 기존 도구가 이미 하는 일은 무엇인가?

### Takeaway
Figma 검사·측정·주석의 축소판이나 토큰 관리 플랫폼을 새로 만들 이유는 약하다. Designary는 기존 작업물에 붙여 넣을 **내용의 구조화와 작은 변환 작업**으로 범위를 좁히는 편이 현실적이다.

### Cited Findings
- **현재 제품 기능; 2026-10-30 열람, 게시일 미표기:** Figma Dev Mode는 거리 측정, 자동 코드 스니펫과 언어/단위 선택, 레이아웃·색·타이포·텍스트·컴포넌트 속성·변수 검사, 변수 값/모드/alias chain, 컬렉션 표, 에셋 내보내기를 제공한다. 주석에는 텍스트와 속성을 넣을 수 있다. 문서상 측정·주석 추가는 유료 플랜의 Full seat 및 편집 권한, 열람은 Full/Dev seat 및 보기 권한 조건이다. 가격이나 전체 플랜 기능표를 이 한 페이지에서 일반화하지 않는다. — [Figma Guide to inspecting](https://help.figma.com/hc/en-us/articles/22012921621015-Guide-to-inspecting)
- **기존 대안의 자체 설명; 2026-10-30 열람, 게시일 미표기:** Tokens Studio는 Figma 플러그인과 별도 Studio 플랫폼을 제공한다. 토큰을 Git으로 동기화하고 JSON 또는 CSS·SCSS·JavaScript·iOS·Android용 코드로 변환하는 흐름을 안내한다. 이 사실은 폭넓은 토큰 수명주기 관리가 이미 경쟁이 있는 영역이라는 근거이며 품질 비교 검증은 아니다. — [Tokens Studio Help Center](https://tokens.studio/help-center)
- **표준화 현황; 2025-10-28 고정판:** DTCG Format Module 2025.10은 JSON 기반 토큰 교환 형식을 명시하는 안정된 Community Group 보고서다. W3C Recommendation/공식 W3C Standard 자체는 아니라고 명시한다. dimension은 값과 단위를 구조적으로 다루며 px/rem을 정의한다. 초안 URL은 계속 바뀌므로 구현을 한다면 이 고정판을 기준으로 삼는다. — [Design Tokens Format Module 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/)

### Inferences
- '주석 생성'이라는 이름만으로는 차별화가 어렵다. **주석을 쓰기 전에 놓친 조건을 찾고, 팀이 결정해야 할 항목을 남기는 것**이 더 명확한 가치다.
- 변수 동기화·alias 해결·테마·브랜드·Git 연동을 포함한 토큰 플랫폼은 현재 무로그인·무백엔드·API 키 없는 정적 사이트 범위를 넘어간다. 파일 입출력 변환만은 가능하지만 별도 경쟁력 검증이 필요하다.
- 단위 도구는 Figma 파일 검사 기능을 흉내 내기보다 여러 값을 붙여 넣고 공통 기준값과 함께 한 번에 복사하는 정도가 적절하다. 기존 4배수 계산기의 작은 확장 후보로 취급한다.

### Gaps
- Figma 전체 2026년 제품군의 모든 기능을 감사한 것은 아니다. 위 판단은 현재 공식 검사 가이드에서 확인한 기능과 날짜가 명확한 핸드오프 가이드를 기준으로 한다.
- Tokens Studio의 유료/무료 플랜별 정확한 export 제한은 비교하지 않았고, 가격 우위 주장은 하지 않는다.
- 경쟁 플러그인을 전부 조사하지 않았으므로 '유일한 도구' 또는 '경쟁 없음'이라고 표현할 수 없다.

## 3. Designary에서 우선 검증할 작은 기능과 제외할 범위는?

### Takeaway
우선순위는 **상태·예외 명세 도우미**, 다음은 기존 용어집 안의 **팀 명명 대응표**, 마지막은 기존 계산기 안의 **여러 값 단위 변환**이다. 아래는 제품 제안이며 사용 효과가 검증된 사실이 아니다. 난이도는 현재 React/Vite 정적 앱에서의 상대 추정이다.

### Cited Findings
- 추천의 기반은 팀이 예외·유효성·장애 피드백을 공동 정의한 [우아한형제들 사례](https://techblog.woowahan.com/6305/)와 누락 상태·반응형 조건 설명을 권하는 [Figma 핸드오프 가이드](https://www.figma.com/blog/the-designers-handbook-for-developer-handoff/)다. 이 자료들은 아래 세 도구의 수요나 성과를 직접 입증하지 않는다.
- 무작정 문서의 양을 늘리는 접근은 주석 작성 부담과 정보 과잉을 지적한 [CHI 2023 연구](https://arxiv.org/html/2302.11845v2)와 긴장 관계에 있다. 한 번의 작업 단위를 작게 유지하는 방향으로 해석했다.

### Inferences

#### 후보 A — 상태·예외 명세 도우미: 우선 검증, 난이도 중
- **대상/시점:** 전담 기획·디자인시스템 지원이 부족한 UI·프로덕트 디자이너가 검색 결과·입력 폼·목록 화면을 개발에 전달하기 직전.
- **입력:** 화면 유형(처음에는 폼/검색 목록 2개), 화면명, Figma 링크(참조 텍스트), 상태별 발생 조건·표시 문구·사용자 행동·복구 방식. 각 항목을 `확정 / 미정 / 해당 없음`으로 선택.
- **출력:** 한국어 Markdown/TSV 표 복사 및 로컬 파일 저장. 예: `검색 결과 없음 | 결과 0건 | 검색어 유지 | 조건 초기화 제공 | 확정`. 완성도 점수 대신 미정 항목 수만 표시.
- **실제 쓰임 가설:** 검색 API 실패와 정상적인 결과 없음이 동일한 화면으로 처리되는 것을 전달 전에 발견. Figma 주석 또는 기존 티켓에 표를 붙이고 개발자와 미정 조건만 합의.
- **최소 UI:** 유형 선택 → 짧은 표 편집 → 복사. 상태 프리셋 5~7개, 필요 없는 상태 숨김, 파란색은 선택/복사에만 사용. 그림자·큰 카드·대시보드 불필요.
- **차별성:** 검사·자동 감사를 주장하지 않는다. 디자이너가 제공한 입력으로 명세 빈칸을 드러내고 결정할 내용을 정리한다. 접근성 상태 체크 후보와 별도 제품으로 분리하지 말고 같은 표 안의 질문으로 통합할 수 있다.
- **검증 질문:** 디자이너–개발자 3쌍에게 최근 검색/폼 화면에 적용해 보게 했을 때, 원래 문서에 없던 중요한 조건을 실제로 발견하는가? 작성 시간 대비 개발자의 후속 질문이 줄어드는가? 팀이 같은 정보를 두 번 기록하게 되는가?

#### 후보 B — 팀 명명 대응표: 조건부, 난이도 하
- **대상/시점:** 용어집을 찾아보면서 개발자와 컴포넌트명을 맞추는 초급 디자이너·작은 팀.
- **입력:** 한국어 의미, 디자인에서 쓰는 이름, 개발에서 쓰는 이름, 선택적 variant/state 이름. 예: `검색 입력 / SearchField / SearchInput / loading`.
- **출력:** 한 줄 명명 대응표와 선택한 표기법(camelCase/PascalCase/kebab-case)의 복사 결과. 로컬 저장·JSON 백업. 자동 번역이나 이름의 정답 판정은 제외.
- **사용례:** 같은 컴포넌트를 '검색창', '서치바', 'Input'으로 부르는 회의에서 실제 팀 이름을 합의하고 용어집 항목 옆에 남긴다.
- **차별성:** 범용 case converter보다 기존 용어집에서 팀의 실제 호칭까지 연결하는 점. 다만 Storybook/Figma 컴포넌트명과의 자동 동기화는 없으므로 중복 관리 위험이 높다.
- **검증 질문:** 사용자에게 필요한 것은 용어 뜻인가, 영어 이름 추천인가, 이미 합의한 이름을 찾는 일인가? 대응표를 두 번째 프로젝트에서도 다시 사용하는가?
- **판단:** 독립 내비게이션 도구보다는 용어집의 작은 보조 기능이 적합. 수요가 없다면 구현하지 않는다.

#### 후보 C — 여러 값 단위 변환·복사: 후순위, 난이도 하(제한된 export는 중)
- **대상/시점:** 작은 웹 프로젝트의 spacing 값을 개발자에게 전달할 때. 이미 4배수 계산기를 사용하는 사람.
- **입력:** `4, 8, 12, 16, 24` 같은 값 목록, 단위, rem 기준 px 값, 선택적 이름 prefix.
- **출력:** 기준값 16일 때 `0.25rem, 0.5rem, 0.75rem, 1rem, 1.5rem`과 기준값을 함께 복사. 필요 검증 후 CSS custom properties export 추가. DTCG export는 spacing/dimension만 지원한다고 명시한 후속 범위로 한정.
- **차별성:** 단일 변환 자체는 약하다. 여러 값·값 이름·기준값을 묶어 전달하고 기존 4배수 흐름에서 이동하지 않는 편의가 가설상 차이.
- **정확성 경계:** 변환 기준을 사용자가 조정하고 출력에 남긴다. px 숫자를 무조건 rem으로 바꾸는 것이 좋은 디자인/접근성이라는 주장이나 dp·sp·pt의 맥락 없는 상호 변환은 제외.
- **검증 질문:** 최근 한 달에 숫자 목록을 실제로 수동 변환한 적이 있는가? 개발자가 디자이너의 rem/CSS 출력을 소비하는가, 아니면 이미 있는 토큰을 사용하는가?

#### 처음에는 만들지 않을 것
- **광범위한 디자인 시스템/토큰 생성기:** [Tokens Studio](https://tokens.studio/help-center)의 기존 범위와 크게 겹치며, [DTCG](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/)의 타입·alias·composite를 제대로 다루려면 작은 계산기를 넘는 유지 비용이 든다는 판단. 도메인 규칙·팀 합의는 생성된 JSON만으로 해결되지 않는다.
- **일반 AI 핸드오프 비서:** 현업 근거는 구체적인 조건·맥락·공동 결정의 필요성을 보여준다. API 키·백엔드가 없는 현재 제품 제약 안에서 안정적인 범용 자동 추론을 추가하기보다, 구조화된 질문으로 먼저 수요를 검증하는 편이 합리적이라는 판단.
- **Figma 대체 검사기·자동 완전성 점수·자동 화면 QA:** 현재 [Figma 검사 기능](https://help.figma.com/hc/en-us/articles/22012921621015-Guide-to-inspecting)과 겹치고, 파일/실행 앱을 읽지 않는 브라우저 도구가 실제 누락이나 구현 적합성을 판정할 수 없다. 사용자가 작성한 체크 상태를 검증 결과로 포장하면 안 된다.
- **거대한 범용 QA 체크리스트:** 위 근거를 바탕으로 한 설계 판단. 수십 개 항목을 매번 체크하는 제품 대신 화면 유형별 짧은 질문과 `해당 없음` 처리부터 시험한다.

### Gaps
