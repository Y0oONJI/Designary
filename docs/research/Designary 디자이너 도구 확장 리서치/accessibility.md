# 접근성·시각 QA: 한국어 Figma 사용자에게 어떤 작은 도구가 필요한가

조사 기준일: 2026-10-30. 범위: 기존 UI 용어 사전·4px 계산/복사 도구를 사용하는 한국어 UI/프로덕트 디자이너. 구현하지 않고 기능 가설을 평가했다. 아래에서 **공식 기준**, **현장 관찰**, **제안/추론**을 구별한다. 주요 출처 묶음은 W3C 규범·해설, WebAIM 실측, WebAIM 도구, Figma 공식 도움말, Stark 공식 도움말, Figma 공식 포럼의 직접 사용자 발언 여섯 가지다. 날짜 없는 제품 문서는 모두 조사일에 확인했으며 발행일을 추정하지 않았다.

## 1. 대비 검사는 중요한가, 기존 도구를 다시 만들 가치가 있는가?

### Takeaway

저대비는 실제 웹에서 반복되는 문제지만, 색상 두 개를 넣는 일반 대비 검사기를 독립 기능으로 추가할 차별성은 낮다. Designary에서는 대비 계산 자체보다 **컴포넌트의 상태·사용 맥락을 명시하고 결과를 한국어로 인계하는 작은 보조 기능**으로 검증하는 편이 낫다. 이는 시장 수요 확정이 아닌 제품 가설이다.

### Cited Findings

- **현장 실측, 수요 통계 아님:** WebAIM의 2026년 2월 상위 100만 홈페이지 자동 조사에서 저대비 텍스트가 83.9%의 홈페이지에 탐지되었다. 조사 대상은 전 세계 홈페이지이고, 한국 Figma 디자이너의 요청 빈도나 구매 의향을 측정하지 않는다. 자동 검사는 모든 실패를 잡지 못하며 오류가 없다고 접근성 적합성을 뜻하지 않는다고 보고서 자체가 설명한다. — [WebAIM Million 2026, 조사 2026-02](https://webaim.org/projects/million/)
- **기존 기능:** WebAIM은 전경·배경 HEX, 전경 alpha, 명도 조절, 일반/큰 텍스트·UI 대비 결과, permalink를 이미 제공한다. 한국어만 붙인 두 색 검사기는 기능 중복이 크다는 판단의 근거다. — [WebAIM Contrast Checker, 발행일 미표기](https://webaim.org/resources/contrastchecker/)
- **Figma 네이티브:** 공식 도움말은 모든 플랜에서 사용하는 color picker 안에 대비 검사, AA/AAA 선택, 일반/큰 텍스트·그래픽 분류, 가까운 통과 색상으로 자동 수정 기능을 설명한다. 따라서 ‘Figma에 기본 대비 검사가 없다’는 전제는 틀리다. — [Figma Update fills using the color picker, 발행일 미표기](https://help.figma.com/hc/en-us/articles/360041003774-Update-fills-using-the-color-picker)
- **더 넓은 네이티브 검사:** Figma Check designs는 변수·스타일 불일치 검사 및 대비 검사를 문서화하며, 대상 플랜은 Education K-12·Organization·Government·Enterprise로 표기되어 있다. 이것을 모든 플랜에 있는 단일 color picker 기능과 혼동하지 말아야 한다. — [Figma Check designs, 발행일 미표기](https://help.figma.com/hc/en-us/articles/39592284074263-Check-designs-in-Figma)
- **기존 플러그인:** Stark는 Figma 선택 레이어의 대비 검사·색상 제안, 로컬 변수·원격 라이브러리 색상을 지원한다. ‘변수와 연계한 대비’도 아무 경쟁자가 없는 영역이 아니다. — [Stark Contrast Checker + Color Suggestions, 발행일 미표기](https://www.getstark.co/support/getting-started/using-the-contrast-checker/)
- **직접 사용자 불편, 제한된 질적 증거:** Figma 포럼에서 사용자는 스타일 편집 중 대비 표시가 없는 이유를 질문했고(2025-04-08), 다른 사용자는 변수 표에서 비교 배경색을 지정하고 싶다고 요청했다(2025-07-24). 당시 지원 담당자는 배경 맥락과 light/dark 인스턴스 차이를 이유로 설명했다. 이는 ‘색상 하나의 좋고 나쁨’보다 ‘어느 배경에서 어떤 용도로 쓰는가’가 필요하다는 직접 사례다. 소수 발언이며 한국 사용자 대표 표본이 아니다. 2025년의 불편이 2026년 모든 Figma 화면에 그대로 남았다고 주장하면 안 된다. — [Figma Forum, 2025-04-08~07-24](https://forum.figma.com/ask-the-community-7/why-is-the-accessibility-color-contrast-only-visible-in-direct-color-mode-vs-style-color-where-its-missing-39325)

### Inferences

- 제안 우선순위는 ‘새 대비 계산기’보다 ‘기본·hover·focus·오류 상태마다 전경/배경/역할을 남겨 복사하는 상태 QA 표’가 높다. 공식 기준을 실행 가능한 인계 문장으로 연결하면 기존 용어 사전과도 맞는다.
- 단, Figma를 떠나 수동으로 색을 붙여 넣는 비용이 있다. ‘무료·한국어’만으로 사용 전환을 기대하지 말고, 상태 누락을 찾는지와 인계 시간을 줄이는지를 검증해야 한다.
- Figma API·계정·토큰 가져오기·AI 자동 수정·전체 프레임 분석은 초기 범위에서 제외하는 제안이다. 로컬 입력과 복사 결과만으로 목적을 검증할 수 있다.

### Gaps

- 한국 디자이너가 별도 웹 검사기를 주기적으로 열고 싶은지, 회사에서 Stark를 사용 가능한지, 상태표를 어디에 인계하는지는 확인되지 않았다.
- 포럼의 과거 변수 제약이 현재 완전히 해소됐는지 직접 앱으로 재현하지 않았다. 경쟁사의 최신 기능 목록만으로 시장의 미충족 수요를 단정할 수 없다.

## 2. 포커스·클릭 영역·타이포그래피에서 정확히 어떤 기준과 오해를 다뤄야 하는가?

### Takeaway

작은 도구의 가장 중요한 품질은 숫자를 정확히 쓰고 **계산 가능한 조건과 사람이 판단할 조건을 분리**하는 것이다. 특히 ‘44px가 WCAG AA의 무조건적 최소’, ‘focus는 반드시 2px여야 AA’, ‘본문은 무조건 16px 이상’, ‘줄간격 1.5가 기본 디자인 의무’ 같은 단순화는 피해야 한다.

### Cited Findings

- **공식 기준:** WCAG 2.2의 현재 확인한 Recommendation 판은 2024-12-12이다. 2.4.7 Focus Visible는 AA, 2.4.11 Focus Not Obscured (Minimum)는 AA로, 포커스된 컴포넌트가 제작자 콘텐츠에 의해 완전히 가려지면 안 된다. 1.4.4 Resize Text는 예외를 제외하고 200% 확대 시 콘텐츠·기능 손실이 없어야 한다. — [W3C WCAG 2.2, 2024-12-12](https://www.w3.org/TR/WCAG22/)
- **텍스트 대비 AA:** 일반 텍스트 4.5:1, 큰 텍스트 3:1이다. 큰 텍스트는 원칙적으로 18pt 이상 또는 14pt bold 이상이며 CSS 환산은 약 24px 또는 18.67px bold이다. 이 숫자는 ‘최소 본문 크기’가 아니다. 비활성 컨트롤·순수 장식·로고 등 예외가 있다. 4.499:1을 화면에 4.5로 반올림했다고 통과시키면 안 된다. — [W3C Understanding 1.4.3, 발행일 미표기](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- **비텍스트 대비 AA:** 식별에 필요한 UI 컴포넌트·상태 및 이해에 필요한 그래픽 부분은 인접 색상 대비 3:1이 필요하다. 모든 장식선·버튼 외곽에 무조건 동일 조건을 적용하는 기준은 아니다. 비활성 컴포넌트 및 제작자가 바꾸지 않은 user agent 외형 등의 예외가 있다. — [W3C Understanding 1.4.11, 발행일 미표기](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- **포커스 모양 AAA:** 2.4.13은 포커스 표시 면적이 비포커스 컴포넌트/하위 컴포넌트의 2 CSS px 두께 둘레 면적 이상이고, 동일 픽셀의 포커스 전후 대비가 3:1 이상일 것을 요구한다(예외 있음). 이는 **AAA**이며, 비텍스트 대비의 ‘인접 색상’ 비교와 서로 다르다. ‘2px 테두리면 자동 AA 통과’라는 도구 출력을 만들면 안 된다. — [W3C Understanding 2.4.13, 발행일 미표기](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)
- **클릭 영역 AA:** 2.5.8은 24×24 CSS px 이상이 기본이다. 작아도 해당 타깃 bounding box 중심의 지름 24px 원이 다른 타깃 또는 다른 작은 타깃의 동일 원과 겹치지 않는 spacing 예외가 있다. 동등 기능, 문장 안 타깃, user agent 제어, 본질적 표현 예외도 있다. 시각적 아이콘이 아니라 실제 pointer target을 판단한다. — [W3C Understanding 2.5.8, 발행일 미표기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- **클릭 영역 AAA:** 2.5.5의 기본 크기는 44×44 CSS px이며 역시 예외가 있다. 플랫폼별 pt/dp 권고와 웹 CSS px를 하나의 숫자로 섞지 말아야 한다. — [W3C Understanding 2.5.5, 발행일 미표기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)
- **텍스트 간격 AA:** 1.4.12는 사용자가 line-height 1.5배, 문단 뒤 2배, letter-spacing 0.12배, word-spacing 0.16배로 바꾸더라도 콘텐츠·기능을 잃지 않게 하는 조건이다. 기본 스타일을 이 값으로 디자인하라는 뜻이 아니다. 해당 언어·문자에 쓰이지 않는 속성은 예외다. — [W3C Understanding 1.4.12, 발행일 미표기](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)
- **경쟁 기능:** Stark는 Figma의 터치 타깃 검사와 브라우저 실제 클릭 요소 검사, Figma 포커스 순서 주석과 실제 웹의 탭 순서 표시를 이미 제공한다. 따라서 Designary가 ‘전체 화면 focus 자동 평가’를 더 간단하게 대체한다고 주장할 근거가 없다. — [Stark Touch Targets, 발행일 미표기](https://www.getstark.co/support/getting-started/using-touch-targets/), [Stark Focus Order, 발행일 미표기](https://www.getstark.co/support/getting-started/establishing-focus-order/)

### Inferences

- 계산 결과 레이블은 ‘이 색상 조합의 일반 텍스트 대비 조건 충족’, ‘24×24 크기 조건 충족’, ‘예외 확인 필요’처럼 범위를 명시하는 것을 제안한다. ‘WCAG 준수’, ‘접근성 100점’, ‘가독성 보장’ 같은 전체 판정은 하지 않는다.
- focus 순서·포커스 가림·오류 설명·키보드 동작은 수동 체크 항목이 적합하다. 색 대비를 계산할 수 있다고 그 UI의 의미·동작까지 검증되는 것은 아니다.
- 한국어 문구와 Pretendard의 실제 줄바꿈을 함께 보는 도구는 현재 타깃과 자연스럽게 연결된다. 다만 어떤 폰트 크기·자간이 모든 한국인에게 최적인지 자동 점수화할 근거는 이번 조사에 없다.

### Gaps

- 한국어 프로덕트 팀에서 가장 자주 누락하는 상태가 focus인지, 오류인지, 로딩인지에 관한 대표성 있는 공개 실측을 확보하지 못했다.
- 이 조사는 WCAG의 디자인 관련 조건을 다루며 한국 법적 의무·인증 기준 또는 모든 플랫폼의 접근성 준수를 판정하지 않는다.

## 3. Designary에 맞는 작고 검증 가능한 기능은 무엇인가?

### Takeaway

초기 검증 순서는 **클릭 영역·패딩 계산 → 상태 QA 인계표 → 한국어 텍스트 스트레스 미리보기**를 제안한다. 첫 기능은 기존 4px 계산과 가장 밀접하고, 두 번째는 사전의 용어를 실제 판단에 연결한다. 세 번째는 차별화 가설이지만 사용자 수요 증거가 가장 약하므로 먼저 샘플로 검증한다.

### Cited Findings

- 아래 제안의 기준 근거는 공식 타깃 크기·텍스트 간격·포커스 기준이며, 기존 시장 중복의 근거는 Figma 네이티브 대비 검사와 Stark의 타깃·주석 기능이다. **기준 존재 자체는 아래 도구를 원하는 사용자의 존재나 규모를 증명하지 않는다.** — [W3C Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [W3C Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html), [Figma Color Picker](https://help.figma.com/hc/en-us/articles/360041003774-Update-fills-using-the-color-picker), [Stark Focus Order](https://www.getstark.co/support/getting-started/establishing-focus-order/)

### Inferences

#### 제안 A — 클릭 영역·패딩 계산 (상대 노력: 낮음, 우선 검증)

- **입력:** 아이콘/콘텐츠 너비·높이, 실제 클릭 영역의 가로·세로 패딩, 목표 24 또는 44 CSS px. 웹 기준임을 표시한다.
- **출력:** 최종 클릭 영역, 목표까지 부족한 각 축의 크기, 대칭 패딩 최솟값, 선택 시 4px 단위 올림값. 예: 16×16 아이콘에서 24 목표면 각 방향 4px, 44 목표면 각 방향 14px이며 4px 단위 선택 시 16px로 48×48이 된다. ‘권장 올림’과 ‘규범상 최소’는 별도 표시한다.
- **워크플로:** Figma에서 아이콘 크기 확인 → 수치 입력 → 박스/클릭영역 시각 비교 → `아이콘 16×16 / 클릭영역 48×48 / 패딩 16` 복사 → Auto Layout 또는 개발 인계에 적용.
- **이점/차별화 가설:** 기존 4px 사용자가 같은 화면에서 목표 크기와 패딩을 연결한다. Stark처럼 프레임 스캔을 복제하는 기능이 아니라 작은 계산과 한국어 설명에 집중한다.
- **한계/범위:** 타깃 spacing 예외의 자동 계산은 초기 제외. 목표 미달을 곧바로 전체 실패로 표시하지 않고 예외 확인 링크 제공. DOM 실제 hit area, 겹침, 포인터 이벤트는 검사하지 않는다. 44는 AAA 기준이며 모든 웹 UI의 AA 의무가 아니다.
- **검증 질문:** “최근 아이콘 버튼을 만들 때 보이는 크기와 실제 클릭 영역을 따로 정했나요? 그때 이 계산 결과를 Figma 또는 개발자에게 그대로 옮길 일이 있나요?”

#### 제안 B — 컴포넌트 상태 QA·인계표 (상대 노력: 중간)

- **입력:** 버튼/입력창 중 하나, 상태별 색상·짧은 설명. 기본·hover·focus·disabled·오류·로딩 중 해당 상태만 선택한다. 모든 컴포넌트가 모든 상태를 가져야 한다고 강제하지 않는다.
- **출력:** 상태별 미리보기와 텍스트 대비 수치, 수동 확인 상태(미확인/확인/해당 없음), 한국어 Markdown 인계표 복사. focus 설명에는 ‘표시 있음’, ‘탭 순서’, ‘가림 여부’를 별도 수동 항목으로 둔다. 오류는 색 외에 텍스트/아이콘 등 전달 방식 확인 항목을 둔다.
- **워크플로:** Figma variants를 보며 상태를 한 줄씩 입력 → 숫자 검사와 누락 검토 → 담당자에게 표 복사. 용어를 누르면 기존 사전의 focus/disabled/validation 설명으로 연결하는 구성을 제안한다.
- **이점/차별화 가설:** 도구의 가치는 색 한 쌍 검사보다 ‘확인하지 않은 상태를 남기고 인계하는 것’에 둔다. 직접 변수·배경 맥락을 지정하고 싶다는 Figma 포럼 사례와 방향은 맞지만, 이 형태의 웹 도구 수요는 아직 추론이다.
- **한계/범위:** 입력한 단색 sRGB HEX만 대상으로 한다. 그라데이션·이미지·블렌드·실제 앱 DOM/탭 순서는 제외한다. disabled는 해당 대비 요구의 예외라는 안내를 주고 자동 실패로 세지 않는다. 포커스의 전체 AAA 면적 평가, 스크린리더/ARIA 검사는 범위 밖이다. 순수 수동 체크리스트만 만들면 노력은 낮아지지만, 상태별 대비 계산과 미리보기를 포함한 제안은 중간으로 평가했다.
- **검증 질문:** “최근 개발 인계에서 뒤늦게 추가한 상태가 무엇이며, 이 표를 채우는 수고보다 상태 누락을 줄이는 이득이 더 큰가요?”

#### 제안 C — 한국어 텍스트 스트레스 미리보기 (상대 노력: 중간, 수요 먼저 검증)

- **입력:** 실제 한국어 문구, 컨테이너 너비/높이, 폰트 크기·두께·줄간격·자간. 기본 Pretendard, 숫자/영문/한글 혼합 샘플 및 긴 오류 문구를 제공하는 제안이다.
- **출력:** 기본 설정과 텍스트 200%·간격 override 설정을 나란히 미리보기, 이 샌드박스 내 잘림/넘침 표시, 설정값 CSS·인계 문장 복사. 각 모드는 무엇을 바꾸는지 명시한다.
- **워크플로:** Figma의 짧은 placeholder를 실제 문구로 교체 → 동일 너비에서 줄바꿈/잘림 비교 → 고정높이·최대줄수 위험 확인 → 값을 복사하고 실제 제품 브라우저에서 다시 확인.
- **이점/차별화 가설:** 일반적인 type scale 생성기보다 한국어 실제 UI 문구·긴 오류·텍스트 확대 대응에 집중한다. 스타일을 예쁘게 고르는 기능보다 콘텐츠 손실을 먼저 발견하는 용도다.
- **한계/범위:** 사이트 안 샌드박스의 결과일 뿐 원래 Figma 프레임이나 실제 제품 CSS가 테스트된 것은 아니다. 200% 텍스트 미리보기는 전체 페이지 확대/리플로 테스트를 대체하지 않는다. 간격 preset은 WCAG 시험 조건이며 기본 권장 디자인값이 아니다. 일반 가독성 점수·‘16px 미만은 실패’ 판정은 하지 않는다.
- **검증 질문:** “최근 한국어 문구 길이 또는 글자 확대 때문에 깨진 화면을 실제로 겪었나요? 이 비교 화면이 Figma에서 직접 줄바꿈을 보는 것보다 어느 순간 더 유용한가요?”

#### 공통 제품 범위 제안

- 브라우저 메모리/선택적 localStorage와 클립보드·JSON/Markdown 다운로드로 동작하게 하여 계정·서버·API 비용 없이 검증한다. 클라우드 저장, 조직 권한, Figma 동기화는 추가하지 않는다.
- UI는 한 도구당 입력·미리보기·결과 복사 구조, 기존 Pretendard와 파란색 사용, 작은 radius·최소 그림자, 장식 칩/슬로건 없는 짧은 한국어 레이블을 제안한다. AA/AAA는 장식 배지보다 기준명과 판정 범위를 보여주는 정보로만 사용한다.
- 초기 검증에서 ‘현재 Figma/WebAIM으로 충분하다’는 답이 반복되면 대비 기능은 독립 메뉴로 만들지 않고 기준 링크/예시만 제공한다. 사용자에게서 실제 최근 사례를 듣기 전에는 세 기능 모두를 한 번에 구현하지 않는 것이 합리적이다.

### Gaps

- 노력 등급은 입력 UI·계산·미리보기·판정 예외에 기반한 상대 추정이며 일정/개발 인원 예측이 아니다.
- 기능별 재방문 빈도·학습효과·인계 오류 감소는 측정하지 않았다. 현재 증거로 확정 가능한 것은 기준과 경쟁 기능, 관찰된 웹 문제, 제한된 사용자 불편 사례까지다.
