# Designary, 한국어 화면의 빈틈을 메우는 도구로 확장하기

Designary는 **한국어 화면을 점검하고 필요한 값을 바로 복사하는 작은 실무 도구**로 확장하는 편이 좋다. 우선 검증할 후보는 한국어 경계값 테스트 데이터, 화면·컴포넌트 상태와 예외 명세, 클릭 영역·패딩 계산이다. 제품 가치의 우선순위는 이 순서로 제안하지만, 가장 작은 첫 배포로는 기존 4의 배수 계산기에 클릭 영역 계산을 붙이는 것이 적합하다. 테스트 데이터는 한국어 콘텐츠라는 구체적인 사용 맥락을 만들고, 상태 명세는 기존 UI 용어 사전을 실제 협업에 연결한다. 세 후보 모두 로그인·서버·유료 API 없이 시작할 수 있다. 다만 **이 순위는 출처를 종합한 제품 판단이며, 한국 디자이너의 수요 순위를 관측한 결과는 아니다.**

## Figma 밖으로 나올 만큼 구체적인 일을 맡아야 한다

별도 웹 도구는 사용자가 Figma를 떠나 값을 입력하고 결과를 다시 옮기는 비용을 만든다. 그 비용을 상쇄하려면 한 번에 쓸 결과가 명확해야 한다. Figma는 이미 색상 선택기의 대비 검사, 텍스트 속성·말줄임, Dev Mode의 측정·속성 검사·코드 스니펫·주석을 제공한다. 따라서 일반 대비 검사기나 치수 전달 화면을 다시 만드는 것만으로는 차이가 약하다. ([Figma 색상 선택기](https://help.figma.com/hc/en-us/articles/360041003774-Update-fills-using-the-color-picker), [텍스트 속성](https://help.figma.com/hc/en-us/articles/360039956634-Explore-text-properties), [Dev Mode 검사](https://help.figma.com/hc/en-us/articles/22012921621015-Guide-to-inspecting))

남아 있는 기회는 값을 계산하는 기능 자체보다 **화면을 깨뜨리는 콘텐츠와 아직 결정하지 않은 조건을 드러내는 일**이다. 우아한형제들의 국내 실무 사례는 디자인·기획·개발이 경계 사례, API 응답, 유효성 검사, 장애 UI를 함께 정의했다고 설명한다. Figma의 핸드오프 가이드도 누락된 상태와 반응형 동작을 전달할 것을 권한다. 이는 문제의 존재를 뒷받침하지만, 별도 웹 도구를 반복 사용할 것이라는 증거까지 제공하지는 않는다. ([우아한형제들 디자인 시스템 사례](https://techblog.woowahan.com/6305/), [Figma 핸드오프 가이드](https://www.figma.com/blog/the-designers-handbook-for-developer-handoff/))

## 한국어 테스트 데이터가 가장 선명한 확장 가설이다

**가치 우선순위 높음, 상대 개발 노력 낮음.** 단순한 이름·주소 생성기보다 정상값과 긴 값, 빈 값, 한영 혼합값을 묶어 주는 도구를 제안한다. 사용자는 상품 카드나 목록을 만든 뒤 짧고 보기 좋은 예시를 이 묶음으로 교체해 레이아웃을 확인한다. Content Reel은 이미 Figma 레이어에 콘텐츠를 채우는 흐름을 제공한다. Designary의 차이는 자동 채우기 경쟁보다 한국어 화면에서 확인할 표본을 고르는 데 두어야 한다. Faker에도 한국어 로케일이 있지만 모든 메서드가 현지화되지는 않으므로, 라이브러리 도입만으로 한국어 데이터 품질이 해결되지는 않는다. ([Content Reel](https://contentreel.design/), [Faker 한국어 로케일](https://fakerjs.dev/locales/ko))

예를 들어 입력이 `상품 카드 / 정상·긴 제목·빈 제목`이면 `매일 쓰는 머그컵`, `손잡이가 넓어 편하게 잡는 데일리 무광 머그컵 450mL 2개 세트`, 실제 빈 문자열을 내보낸다. 금액은 `0원 / 19,900원 / 999,999,999원`, 추가 표본은 `띄어쓰기없이이어지는긴상품명`이나 `Designary 디자인팀`처럼 형태를 달리한다. 이 예시는 직접 작성한 제품 제안이다. 사용자가 확인할 것은 “긴 이름이 몇 줄을 차지하는가”, “가격이 커져도 정렬되는가”, “내용이 없을 때 무엇이 남는가”다.

첫 MVP는 **상품명·금액·상태 문구의 검수된 작은 묶음과 개별·줄바꿈 목록 복사**로 한정한다. 생성 개수나 다운로드 형식을 늘리기보다 정상·긴 값·빈 값의 차이를 빠르게 선택하게 한다. 화면의 `빈 값` 안내와 실제 복사되는 빈 문자열을 구분하고, 모든 콘텐츠를 샘플로 표시한다. 실주소나 전화번호까지 범위를 넓힐 필요는 없다. 실제처럼 생성한 데이터가 우연히 실제 정보와 일치할 수 있다는 점도 고려할 이유다. ([Faker 공식 저장소](https://github.com/faker-js/faker))

한계는 Figma 선택 레이어에 자동으로 채워지지 않는다는 점이다. 줄바꿈 목록이나 추후 CSV·JSON 출력도 자동 배치를 보장하지 않는다. **검증 질문은 “최근 직접 만들었던 더미 값 중 기존 플러그인으로 해결되지 않은 것이 무엇이며, 이 묶음을 실제 화면에 붙이는 과정이 편한가?”**다. 현재 방식과 비교해 수정 횟수와 빠뜨렸던 경계 사례를 관찰해야 한다. 한국어 지원 자체를 수요의 증거로 삼아서는 안 된다.

## 상태·예외 명세는 용어를 팀의 결정으로 연결한다

**가치 우선순위 높음, 상대 개발 노력 중간.** 사용자가 검색 목록이나 입력 폼을 개발에 전달하기 직전에 발생 조건, 표시 문구, 사용자 행동, 복구 방식을 짧은 표로 정리하게 한다. 검색 결과 0건과 요청 실패를 구분하고, 제출 중 재클릭이나 실패 후 입력 유지처럼 화면 한 장으로 드러나지 않는 결정을 남기는 도구다. 국내 협업 사례와 Figma 가이드가 이 방향을 지지한다. 반면 미국 UX 실무자 114명을 다룬 CHI 2023 연구는 주석 작성 부담과 정보 과잉도 지적한다. 따라서 긴 체크리스트보다 필요한 질문만 보여주는 편이 적합하다. 이 연구는 미국 표본이며 현재 한국 팀의 상황을 그대로 대표하지 않는다. ([국내 협업 사례](https://techblog.woowahan.com/6305/), [Figma 핸드오프 가이드](https://www.figma.com/blog/the-designers-handbook-for-developer-handoff/), [CHI 2023 연구](https://arxiv.org/html/2302.11845v2))

입력이 `검색 목록 / 결과 0건 / 검색어 유지 / 조건 초기화 제공`이면 출력은 `결과 없음 | 정상 응답 0건 | 검색어 유지 | 필터 초기화 | 확정` 같은 복사용 한 줄이다. 요청 실패는 별도 행으로 두고, 복구 방식이 정해지지 않았다면 `미정`을 남긴다. 사용자는 Figma를 보며 표를 채운 뒤 기존 티켓이나 인계 문서에 붙인다. 모든 상태를 완성하도록 강요하지 않고 `확정·미정·해당 없음`을 구분하는 것이 핵심이다.

첫 MVP는 **검색 목록·입력 폼 두 유형, 필요한 상태 선택, 조건·문구·행동 편집, Markdown 또는 TSV 복사**다. 접근성은 별도 검사 제품으로 분리하지 않고 “오류를 색 이외의 정보로도 전달하는가”, “키보드 포커스가 보이는가”, “포커스 순서를 확인했는가” 같은 수동 질문으로 묶는다. 관련 용어에서 기존 사전으로 이동하면 용어를 이해한 다음 결정을 기록하는 흐름이 생긴다. 색상 대비 계산과 미리보기는 이 표의 효용을 확인한 뒤 추가해도 된다. WCAG는 포커스 표시와 가림 등을 실제 동작 조건으로 다루므로, 체크 표시를 자동 적합성 판정으로 바꾸면 안 된다. ([WCAG 2.2](https://www.w3.org/TR/WCAG22/))

한국어 상태 문구도 이 안에 보조 예시로 넣는 편이 좋다. `검색 결과가 없어요 / 다른 검색어로 찾아보거나 필터를 줄여보세요 / 필터 초기화`처럼 원인과 다음 행동을 연결하되, 필터가 없는 화면에는 마지막 행동을 제공하지 않는다. 토스플레이스 가이드도 다음 행동이 드러나는 오류·버튼 문구를 안내하지만, 해당 제품의 말투와 세부 규칙을 모든 한국어 UI의 정답으로 일반화할 수는 없다. ([토스플레이스 UX 라이팅](https://docs.tossplace.com/guide/front-integration/plugin/design/ux-writing.html))

한계는 파일이나 실행 앱을 읽지 않고 사용자가 입력한 내용만 정리한다는 점이다. 팀이 이미 충분한 명세를 관리한다면 중복 기록이 된다. 실제 복구 가능성이나 입력값 보존 여부를 도구가 추정해서도 안 된다. **검증 질문은 “최근 뒤늦게 추가한 상태가 무엇이며, 이 표가 원래 문서에 없던 중요한 조건을 발견하게 하는가?”**다. 복사 횟수보다 작성 부담, 새로 드러난 미정 조건, 개발자가 받았을 때의 유용성을 확인해야 한다.

## 클릭 영역·패딩 계산은 가장 작게 배포할 수 있다

**가치 우선순위는 앞선 두 후보 다음, 상대 개발 노력은 가장 낮음.** 기존 4의 배수 도구에 아이콘 크기와 실제 클릭 영역의 관계를 추가한다. 사용자는 Figma에서 아이콘 크기를 확인하고 목표 영역을 선택한 뒤, 필요한 패딩과 4px 단위 올림 결과를 복사한다. 새 작업 방식을 배우게 하기보다 이미 있는 숫자 복사 흐름에 구체적인 목적을 붙인다는 장점이 있다.

입력 `아이콘 16×16 / 목표 44×44 CSS px`의 출력은 대칭 패딩 `14px`다. 각 방향 패딩을 4px 단위로 올리면 `16px`, 최종 영역은 `48×48`이 된다. 복사 문장은 `아이콘 16×16 / 클릭 영역 48×48 / 상하좌우 패딩 16`으로 충분하다. 목표를 `24×24`로 바꾸면 각 방향 패딩은 `4px`다. 첫 MVP는 가로·세로 크기, 목표 크기, 대칭 패딩, 선택적인 4px 올림과 복사만 포함한다.

기준 표시는 정확해야 한다. **WCAG 2.2 AA의 2.5.8은 기본적으로 24×24 CSS px, AAA의 2.5.5는 기본적으로 44×44 CSS px를 다룬다.** 둘 다 예외가 있으며 44px가 모든 웹 UI의 AA 의무는 아니다. 특히 AA에는 작은 타깃 중심의 지름 24px 원이 다른 타깃 또는 다른 작은 타깃의 해당 원과 겹치지 않는 간격 예외가 있다. 문장 안 타깃 등 다른 예외도 있으므로 목표보다 작다는 이유만으로 접근성 전체 실패를 표시해서는 안 된다. ([W3C 타깃 크기 AA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [타깃 크기 AAA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html))

한계는 실제 클릭 영역, 겹침, 포인터 이벤트를 검사하지 못한다는 점이다. 플랫폼별 pt·dp 권고도 웹 CSS px와 섞지 않는다. 결과는 `선택한 크기에 필요한 패딩`으로 표현하고 예외 확인 링크를 둔다. **검증 질문은 “최근 아이콘과 클릭 영역을 따로 정한 사례가 있으며, 이 출력이 Figma Auto Layout이나 개발 전달에 바로 쓰이는가?”**다. 계산이 쉽다는 사실만으로 독립 메뉴를 만들 이유는 없으므로 기존 계산기 안의 작은 확장으로 시작한다.

## 후속 후보는 남기되, 첫 검증의 범위를 좁힌다

용어 사전에는 `검색 입력 / 디자인명 SearchField / 개발명 SearchInput`처럼 팀 명명 대응표를 붙일 수 있다. 다만 별도 이름 관리 도구는 Figma·Storybook과 중복되므로, 사용자가 이미 합의한 이름을 다시 찾는 문제가 있는지 확인한 후 추가한다. 한국어 줄바꿈 비교도 후속 후보지만, 일반 폰트 미리보기보다 한영 혼합·긴 어절을 같은 폭에서 `normal`과 `keep-all`로 비교하는 데 한정하는 것이 좋다. CSS의 두 정책은 한국어 줄나눔에 차이를 만들지만, 이것만으로 도구 수요가 입증되지는 않는다. ([CSS Text Level 4](https://www.w3.org/TR/css-text-4/))

독립 대비 검사·범용 타이포 도구·일반 단위 변환은 후순위다. Figma의 기존 기능과 겹치고, 단위 변환은 기존 계산기의 보조 기능으로 충분한지 먼저 볼 수 있다. 전체 디자인 토큰 생성·동기화는 Tokens Studio 같은 대안과 경쟁하면서 현재 앱의 유지 범위를 크게 넓힌다. 범용 AI 채팅도 현재의 무서버·무API 비용 조건에서 우선할 이유가 약하다. ([Figma 텍스트 속성](https://help.figma.com/hc/en-us/articles/360039956634-Explore-text-properties), [Figma 크기 조절·연산](https://help.figma.com/hc/en-us/articles/360039956914-Adjust-alignment-rotation-position-and-dimensions), [Tokens Studio](https://tokens.studio/help-center))

다음 조사는 **Figma를 쓰는 한국 디자이너 3~5명에게 제안하는 소규모 사용성 검증**이다. 이미 조사한 표본이 아니다. 최근 상품·목록·폼 화면 한 개와 현재 쓰는 도구를 가져오게 하고, 먼저 실제로 번거로웠던 일을 듣는다. 준비한 테스트 데이터 묶음을 붙여 보고, 상태 표로 한 화면을 정리하고, 아이콘 하나의 패딩을 계산하게 한다. 현재 방식 대비 수정 부담, 새로 발견한 문제, 결과가 실제로 붙여 넣어지는 위치를 관찰한다. 가능하면 상태 표를 받을 개발자의 반응도 확인한다. 다음 실제 작업에서 다시 썼는지 후속 확인하면 첫인상의 호감과 반복 효용을 구분할 수 있다.

첫 배포 범위는 클릭 영역 계산 하나로 제한하되, 이를 전체 제품 방향의 검증으로 오해하지 않는다. 더 큰 확장 여부는 한국어 데이터와 상태 명세의 실제 작업 결과를 보고 정한다. UI도 입력·결과·복사를 중심으로 기존 Pretendard, 파란색, 작은 모서리와 최소 그림자를 유지하면 된다. 기능 수보다 “실제 화면 하나에서 무엇을 해결했는가”가 다음 투자를 결정하는 기준이다.

## 출처의 강도와 판단의 한계

조사 기준일은 2026-10-30이다. W3C 자료는 기준과 예외를 확인하는 근거이며 수요 자료가 아니다. Figma·Content Reel·Faker·Tokens Studio 공식 문서는 현재 제공 기능과 중복 범위를 판단하는 데 사용했다. 국내 당사자의 우아한형제들 사례는 구체적인 협업 문제를 보여주지만 한 조직의 경험이고, CHI 연구는 체계적인 조사이나 미국 표본·과거 도구 환경이라는 한계가 있다. 본문에 연결한 원문이 주요 출처이며, 날짜 없는 제품 문서의 발행일은 추정하지 않았다.

현재 확인되지 않은 것은 한국 디자이너의 기능별 사용 빈도, 별도 웹 도구로 이동할 의향, 반복 사용률이다. 개발 노력도 정적 React 앱에서 입력·복사·로컬 데이터로 제한했을 때의 상대 판단이며 일정 추정이 아니다. 이번 보고서는 제공된 조사 노트의 종합과 제품 제안으로, 앱 구현이나 자동 접근성 감사를 수행한 결과가 아니다.
