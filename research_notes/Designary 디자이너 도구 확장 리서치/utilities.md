# 반복 실무 도구와 한국어 콘텐츠·현지화

## 1. 반복적으로 채워 넣는 콘텐츠에서 어떤 기회가 있는가?

### Takeaway
우선 검증할 후보는 **한국어 UI 샘플 데이터 + 경계값 묶음**이다. 일반 더미 텍스트 생성은 이미 대안이 있으므로, 이름·상품명·금액을 만드는 것보다 정상/긴 값/빈 값/혼합 언어를 함께 주는 데 차별화 가설을 둔다.

### Cited Findings
- Microsoft의 Content Reel은 Figma에서 하나 이상의 레이어를 선택해 텍스트·아바타·아이콘을 넣고, 자체 텍스트 콘텐츠를 만들거나 순서/랜덤/정렬 방식으로 적용하는 기능을 안내한다. 따라서 단순 복사용 텍스트 사이트는 Figma 내부 작업 흐름과 경쟁한다. 게시일 미표시, 2026-10-30 확인. — [Content Reel 공식 소개](https://contentreel.design/)
- Figma 사용자 커뮤니티의 한 댓글은 표를 만들 때 준비된 템플릿으로 셀을 빠르게 채우고 자체 템플릿을 만들 수 있어 Content Reel이 유용하다고 보고한다. 페이지는 확인 시 약 2년 전으로 표시된다. 이는 특정 반복 작업의 실제 경험이지만 단일 자기보고이며 한국 디자이너의 보편적 빈도 증거는 아니다. — [Reddit: 자주 사용하는 Figma 플러그인](https://www.reddit.com/r/FigmaDesign/comments/1ekdct1/what_are_some_musthave_figma_plugins_that_you_use/)
- Faker는 한국어 `fakerKO`를 제공하지만 모든 메서드가 현지화되는 것은 아니라고 명시한다. 확인 당시 한국어 데모의 일부 상품명·동사는 영어였으며, 원 저장소는 미지원 로케일 데이터에 영어 fallback을 설명한다. '한국어를 지원한다'는 사실만으로 한국어 상품·주소 데이터 품질을 보장할 수 없다. 게시일 미표시, 2026-10-30 확인. — [Faker 한국어](https://fakerjs.dev/locales/ko), [Faker 공식 저장소](https://github.com/faker-js/faker)
- Faker는 브라우저에서 실행 가능하며, 실제처럼 만든 이름·주소·이메일 등이 우연히 실제 정보와 일치할 수 있다고 알린다. — [Faker 공식 저장소](https://github.com/faker-js/faker)

### Inferences
**후보 A — 한국어 화면 데이터 팩. 구현 난도 낮음, 추천 우선순위 높음(제품 가설).**

- 사용 상황 가설: 상품 카드·회원 목록·주문 테이블·프로필을 반복 제작할 때 내용 채우기와 레이아웃 점검을 함께 한다.
- 입력 예: `상품 카드 / 정상+긴 제목+빈 제목 / 3개`.
- 직접 작성한 출력 예: 정상 제목 `매일 쓰는 머그컵`; 긴 제목 `손잡이가 넓어 편하게 잡는 데일리 무광 머그컵 450mL 2개 세트`; 빈 제목은 실제 빈 문자열로 복사하되 화면에는 `빈 값` 표시. 금액 `0원`, `19,900원`, `999,999,999원`을 별도 경계값으로 제공.
- 1차 범위: 소수의 검수된 이름·상품명·금액·날짜·상태 문자열 데이터셋, 짧음/보통/김/빈 값 탭, 개별 복사와 줄바꿈 목록·CSV·JSON 복사. 임의의 정확한 실주소/연락처를 기본 제공하기보다 명확한 샘플을 사용한다. CSV는 쉼표/따옴표/줄바꿈을 올바르게 인코딩하고, JSON은 실제 빈 문자열과 표시용 `빈 값` 라벨을 구분한다.
- 차별점 가설: '랜덤 100개'보다 `정상 + 화면을 깨뜨릴 수 있는 값`을 한 묶음으로 제공. `긴상호명이띄어쓰기없이이어지는경우`, `Designary 디자인팀`, 이모지와 숫자 혼합, 누락된 데이터처럼 형태가 다른 표본을 명시적으로 포함.
- 정적 구현 판단: 검수된 로컬 데이터와 클립보드만으로 시작 가능하므로 API·로그인·서버가 필요하지 않다. Faker 전체를 넣어 콘텐츠 품질을 해결했다고 간주하지 않는다.
- 한계: **현재 정적 웹 범위에서 Figma 선택 레이어 자동 채우기/동기화는 미지원**이다. 줄 단위 복사 결과가 사용자의 현재 붙여넣기 방식에 맞는지 검증해야 하며, CSV/JSON은 다른 도구나 개발 샘플에 전달하는 형식이지 Figma 자동 배치를 보장하지 않는다. 생성된 데이터와 실제 고객 데이터는 구분해서 표시한다.

### Gaps
- 한국 디자이너가 이름/주소/상품/커머스/어드민 중 무엇을 얼마나 자주 채우는지 신뢰할 만한 정량 자료를 찾지 못했다.
- 확인 질문: 최근 화면에서 직접 더미 값을 만든 사례가 있는가? 한 번에 몇 개를 필요한가? Content Reel/기존 컴포넌트의 샘플로 해결되지 않는 값은 무엇인가? 긴 값과 빈 값까지 실제로 검토하는가?
- 검증 과제: 같은 표를 기존 방식과 데이터 팩으로 각각 채워 보고 완료 시간, 수동 수정 수, 다시 쓸 의향을 관찰한다. 존재하는 플러그인 수를 수요 규모로 해석하지 않는다.

## 2. 한국어 UX 상태 문구 도구는 어떤 문제에 집중해야 하는가?

### Takeaway
한국어 상태별 문구 템플릿은 작은 정적 도구로 가능하다. 다만 특정 기업의 말투를 정답으로 강제하거나 범용 자동 교정기로 만들기보다 **상황·원인·다음 행동을 묶어 선택하는 참고 도구**가 적합하다는 가설이다.

### Cited Findings
- 토스 UX Writer 김자유는 모든 제품 문구를 직접 검수하는 데 한계가 있어 다른 사람이 잘 쓸 수 있는 규칙과 시스템을 만드는 방향으로 전환했다고 설명한다. 2023-04-14 게시된 실무자의 1차 경험담이다. 개별 회사의 사례이며 모든 조직에 같은 효과가 난다는 증거는 아니다. — [첫 UX writer는 무슨 일을 해야 할까](https://toss.tech/article/1st_uxwriter)
- 토스플레이스의 실제 제품 가이드는 에러 메시지에서 다음 행동을 알려주고, 버튼은 누른 뒤 일어날 일을 알 수 있도록 쓰도록 안내한다. 동시에 사용자(손님/직원)와 상황에 따라 문구 기준을 구분한다. 게시일 미표시, 2026-10-30 확인. — [토스플레이스 UX 라이팅](https://docs.tossplace.com/guide/front-integration/plugin/design/ux-writing.html)
- 해당 가이드의 해요체·이모지 금지·다이얼로그 왼쪽 버튼명 규칙은 그 제품에 대한 규칙이다. 출처 자체가 프론트/POS 화면의 작성 기준으로 범위를 명시한다. 이를 한국어 UX 전체의 규범으로 일반화하면 안 된다. — [토스플레이스 UX 라이팅](https://docs.tossplace.com/guide/front-integration/plugin/design/ux-writing.html)

### Inferences
**후보 B — 상태별 한국어 UX 문구 카드. 구현 난도 낮음, 콘텐츠 검수 부담 중간, 추천 우선순위 중간(제품 가설).**

- 입력 예: `검색 / 결과 없음 / 해요체`.
- 직접 작성한 출력 예: 제목 `검색 결과가 없어요`; 설명 `다른 검색어로 찾아보거나 필터를 줄여보세요.`; 행동 `필터 초기화`. 필터가 없는 화면이라면 해당 행동을 제거하라는 사용 조건을 함께 표시한다.
- 두 번째 입력 예: `저장 / 실패 / 원인 미확인 / 다시 시도 가능` → 제목 `저장하지 못했어요`; 행동 `다시 시도`. 실제로 확인되지 않은 네트워크 장애나 '입력한 내용이 안전하게 보관됨'을 자동으로 단정하는 설명은 생성하지 않는다.
- 1차 범위: 빈 상태·검색 결과 없음·입력 오류·처리 중·성공·재시도 가능한 오류처럼 소수의 상황, 제목/설명/버튼 세트 복사, 말투 두 종류, 적용 조건과 수정할 변수 표시. 완성된 브랜드 보이스 생성보다 편집 가능한 출발점으로 제공한다.
- 차별점 가설: 좋은 문장 모음만 보여주지 않고 `처음이라 데이터가 없음 / 검색 조건에 맞는 값이 없음 / 데이터를 불러오지 못함`을 구분한다. 기존 UI 용어 사전에서 해당 상태의 의미와 예시 도구를 연결할 수 있다.
- 정적 구현 판단: 직접 집필하고 검수한 템플릿과 슬롯 입력으로 충분하다. 자동 생성 모델/유료 API는 필요하지 않다.
- 한계: 템플릿은 실제 복구 가능성, 입력값 유지 여부, 금융·의료 등의 정책을 판단하지 못한다. 외부 가이드의 예시 문장을 대량 복제하지 않고 원칙을 참고해 자체 예시를 작성한다. 모든 상황에 해요체를 강제하지 않는다.

### Gaps
- 디자이너가 팀 라이팅 가이드 없이 문구를 결정하는 비율이나 템플릿 도구 재방문 빈도는 확인하지 못했다.
- 확인 질문: 실제 어려움이 초안 작성인가, 팀 말투 정렬인가, 원인/복구 조건을 몰라 쓰지 못하는 것인가? 팀에 이미 쓰는 문구 라이브러리가 있는가? 제목/설명/버튼 중 무엇을 자주 재작성하는가?
- 검증 과제: 최근 오류/빈 상태 화면 한 개를 가져와 이 도구로 수정하게 하고, 문구 복사 횟수보다 조건에 맞게 선택했는지와 수정 부담을 확인한다.

## 3. 타이포그래피 미리보기·크기 변환은 어디까지 확장할 가치가 있는가?

### Takeaway
일반 폰트 미리보기나 종횡비 계산만으로는 기존 Figma와 중복이 크다. 후속 후보로는 **한국어 텍스트가 실제 브라우저에서 줄바꿈되는 모습을 비교하는 작은 실험 도구**가 더 구체적이다. 수치 변환은 기존 4배수 도구의 보조 기능으로 검토한다.

### Cited Findings
- Figma는 글꼴/행간/자간 등 타입 설정 미리보기, 텍스트 말줄임, 최대 행 수 설정을 제공한다. 따라서 '한글을 입력해 폰트 크기를 보는 화면' 자체는 새로운 기능이 아니다. 게시일 미표시, 2026-10-30 확인. — [Figma 텍스트 속성](https://help.figma.com/hc/en-us/articles/360039956634-Explore-text-properties)
- Figma는 위치 필드의 기본 수식 연산과 레이어 종횡비 잠금을 안내한다. 종횡비 잠금은 너비 또는 높이 변경 시 다른 치수를 함께 조절한다. 별도 비율 계산기로 이동하는 가치가 항상 있는 것은 아니다. 게시일 미표시, 2026-10-30 확인. — [Figma 정렬·위치·크기 조절](https://help.figma.com/hc/en-us/articles/360039956914-Adjust-alignment-rotation-position-and-dimensions)
- W3C의 한국어 레이아웃 요구사항 문서는 한글 줄나눔에 글자 단위와 어절 단위 접근이 있음을 설명한다. 확인한 판은 **2026-03-21 Group Note Draft**이며, 확정 표준이나 W3C 회원의 승인 문서로 소개해서는 안 된다. — [한국어 텍스트 레이아웃 요구사항](https://www.w3.org/TR/klreq/?lang=en)
- CSS Text Level 4는 한국어 줄나눔의 `word-break: normal`과 `keep-all` 차이를 설명한다. MDN은 `rem`이 루트 요소 글꼴 크기를 기준으로 함을 설명한다. 따라서 '한국어는 언제나 어절 단위' 또는 '1rem은 언제나 16px'로 고정하면 부정확하다. 2026-10-30 확인. — [CSS Text Level 4](https://www.w3.org/TR/css-text-4/), [MDN font-size](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/font-size)

### Inferences
**후보 C — 한국어 줄바꿈·텍스트 폭 실험실. 구현 난도 중간, 추천 우선순위는 A/B 검증 이후(제품 가설).**

- 입력 예: 문장 `배송 정보를 확인하고 다음 단계로 진행해주세요`, 너비 `240px`, Pretendard `16px`, 행간 `24px`, 최대 `2행`.
- 출력: 같은 조건에서 `normal`과 `keep-all`을 나란히 렌더링하고 말줄임 켜기/끄기, 200% 글자 크기 비교, 적용한 CSS를 복사한다. 특정 문장이 몇 줄이 된다고 사전 단정하지 않고 실제 렌더링 결과를 보여준다.
- 1차 범위: 앱에서 실제 로드되는 하나의 폰트, 사용자가 입력한 문장, 2개의 줄바꿈 정책, 고정 너비와 글자 크기/행간 슬라이더. 후보 A의 긴 상품명·공백 없는 텍스트를 바로 불러올 수 있게 한다.
- 차별점 가설: 폰트 구경보다 한영 혼합·숫자·괄호·긴 어절의 줄바꿈과 실제 CSS를 연결한다. React 정적 페이지에서 렌더링 가능한 범위라 서버는 필요하지 않다.
- 한계: 브라우저·폰트 로드·대체 폰트에 따라 결과가 달라진다. Figma와 픽셀 단위로 동일함을 보장하는 도구로 소개하지 않는다. 정규식으로 한국어 문장을 잘라 임의로 말줄임을 재현하지 않는다. 콘텐츠 잘림을 자동으로 접근성 합격/불합격 판정하는 것도 범위 밖이다.

**수치 변환은 독립 메뉴보다 기존 계산기 확장 후보(구현 난도 낮음).**

| 작은 기능 | 입력 → 출력 예 | 우선순위 판단(가설) |

| 비율/한 변 계산 | `16:9`, 너비 `360` → 높이 `202.5` | Figma 종횡비 잠금과 겹침. 여러 규격을 한 번에 복사해야 하는 경우가 있는지 먼저 확인 |
